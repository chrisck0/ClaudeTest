# Github Issue 등록

> 워크플로우 `2. Github Issue` 단계를 수행하는 스킬.
>
> 이 스킬은 **절차와 멘트 규격**만 정의한다. 섹션별 작성 규칙은 아래 원본 문서를 읽고 따른다. (규칙의 단일출처 유지)

## 절차

1. **권유** : `WorkflowRules.md`의 기준으로 등록 필요 여부를 판단하고, [권유 멘트](#1-권유-멘트)로 권유한다.
   - 사용자가 Issue 작성을 직접 요청한 경우, 권유를 생략하고 2번으로 넘어간다.
   - 사용자가 Issue 생성을 하지 않도록 명시한 경우(예 : 작업지시서) 이 스킬을 중단한다.
   - 거절 시 Issue 없이 `3. 브리핑`으로 넘어간다.
2. **배경 / 목적 확인** : [질문 멘트](#2-배경--목적-질문-멘트)로 사용자에게 질문한다. 답을 받지 못하면 작성을 거부한다.
3. **초안 작성** : 참조 문서를 읽고 양식에 맞춰 초안을 작성한다.
   - 작성 규칙에 따라 질문이 필요하면, 초안 작성 전에 [작성 전 확인 멘트](#3-작성-전-확인-멘트)로 한 번에 질문한다.
4. **승인** : [승인 멘트](#4-작성-전-승인-멘트)로 초안을 보여주고 승인을 받는다. 수정 요청 시 3번으로 돌아간다.
5. **등록** : `gh issue create`로 등록한다.
   - 등록 전 `gh auth status`로 인증 상태를 확인한다.
   - Title은 `--title`로 전달하고, 본문에서는 `# [Title]` 줄을 제외한다.
   - 본문은 세션 임시(scratchpad) 디렉터리에 UTF-8 파일로 저장한 뒤 `--body-file`로 전달한다.
   - Label이 없으면 `gh label create`로 먼저 생성한다. 신규 생성 여부는 4번 승인 멘트에 표시해 승인받은 경우에만 생성한다.
6. **안내** : [완료 멘트](#5-등록-완료-멘트)로 Issue 번호를 알린다.

### 예외 처리

- 아래 경우에는 임의로 재시도하거나 우회하지 않고, [실패 멘트](#6-등록-실패-멘트)로 보고한 뒤 사용자의 지시를 기다린다.
  - `gh` 인증이 되어 있지 않은 경우 : 사용자에게 `! gh auth login` 실행을 안내한다.
  - `gh label create`, `gh issue create`가 실패한 경우 : 오류 메시지를 그대로 전달한다.

## 멘트 규격

- 각 멘트는 아래 형식만 사용하고, 형식 밖의 설명을 덧붙이지 않는다.
- `[ ]` 안은 한 줄로 작성한다.

### 1. 권유 멘트

```markdown
**Issue 등록 권유**
- 유형 : [개발 / 버그 수정]
- 사유 : [권장 이유 한 줄]
- 예상 Label : [Label]

Issue를 작성할까요?
```

### 2. 배경 / 목적 질문 멘트

```markdown
Issue의 `배경 / 목적`을 알려주세요.
- 왜 이 작업이 필요한가요?
- 이 작업으로 무엇을 해결하려 하나요?
```

### 3. 작성 전 확인 멘트

- 질문이 여러 개면 번호를 늘려 같은 형식으로 적는다.
- 선택지는 `A.`, `B.`, `C.` 순으로 알파벳을 붙여 나열한다. 선택지가 없으면 `없음`으로 적는다.

```markdown
**Issue 작성 전 확인**
1. [질문]
   - 확인한 내용 : [근거가 된 사실]
   - 선택지 : [A. 선택지 / B. 선택지 ... / 없음]

답변은 `1A, 2B`처럼 주시면 초안을 작성하겠습니다.
```

### 4. 작성 전 승인 멘트

```markdown
**Issue 초안**
- Label : [Label] [(신규 생성) / (기존)]

(IssueTemplate 양식의 본문 전체)

이대로 등록할까요?
```

### 5. 등록 완료 멘트

```markdown
Issue #[번호] 등록 완료 : [URL]
```

### 6. 등록 실패 멘트

```markdown
**Issue 등록 실패**
- 단계 : [인증 확인 / Label 생성 / Issue 등록]
- 오류 : [오류 메시지]
- 조치 : [사용자가 할 일]
```
